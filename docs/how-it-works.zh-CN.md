# 技术思路（详细版）

这里讲四个核心思路的来龙去脉：机理、实测数字、以及走过的死路。不含源码。

## 一、时间轴：用你自己的手指当时钟

### 为什么"猜"不行

音游首先需要一个数：**谱面时间 `t = 0` 对应现实里的哪一刻？** 这个游戏里，
谱面文件里没有前摇时长，加载时间又不固定。

同一台设备、同一首歌、同一套逻辑，在同一天里的实测：

| 第几次 | "点开始键到谱面时间 0" |
| --- | --- |
| 1 | 2.12 秒 |
| 2 | 9.53 秒 |
| 3 | 10.05 秒 |
| 4 | 11.52 秒 |

最大差 9 秒。所以任何写死的常数大部分时候都是错的——而且错了不是"差一点"，
是整首歌全 miss。

用画面检测"演奏画面什么时候出现"可以，但视频链路本身有 25~40ms 延迟、还会偶发误检，
拿它当时钟等于给每个音符都加了一个未知常数偏移。我们也试过闭环修正（看屏幕上的音符
反推偏移），结果检测一误判就把整段推偏几百毫秒。

### 换成了什么

手机自己的触摸屏驱动会给每个触摸事件打上**内核时间戳**。你按下第 1 个音符、游戏判了它，
那个时间戳**就是**游戏眼里的谱面时间 `t1`。

于是脚本：

1. 开演前先挂上真实触摸屏的读取（`getevent`）；
2. 取演奏区里第一次落指的**内核时间戳** `F`；
3. 剩下的音符全部排到 `F + (t_n − t_1)`。

两个后果很关键：

* **读得慢不影响精度**——时间戳是内核时间，不是我们收到的时刻，读得慢只会让我们晚一点开打；
* **注入链路里的固定延迟会自己抵消**——你的手指和脚本的注入走的是同一条输入链路。

剩下的误差就是你那一下自己的时序误差。对**快滑条**这个残差仍然看得见
（50ms × 4000px/s ≈ 200px），这也是后来做"连续跟随"的原因。

### 延迟是量出来的

要把内核时间戳换算成本机时刻，还需要知道 `L + λ`（读取延迟 + 注入延迟）。
脚本会在**加载页**用虚拟触摸屏点几下、看设备端多久读到，实测 **≈ 1ms**
（常驻 adb shell 自身往返 0.7~1.5ms，吻合）。

## 二、注入：虚拟 HID 触摸屏，不用 root

在现代原厂安卓上：

| 方式 | 结果 |
| --- | --- |
| 直接写 `/dev/input/eventN` | 被 SELinux 拒绝（`u:object_r:input_device:s0`） |
| `adb shell input tap` / `motionevent` | 能用，但只能单指、每次 60~80ms |
| **scrcpy-server UHID** | 可用：系统里注册出一块真正的 `TOUCH \| TOUCH_MT` 数字化仪 |

UHID 允许一个**普通进程（非 root）**把自己写的 HID 报告描述符交给内核，让内核凭空造出一个
HID 设备。给它一份多点触摸屏的描述符，系统就当成真实面板硬件，游戏无法区分。

两个花了不少时间才踩明白的细节：

* 描述符里的 Logical Maximum 必须用**面板自然方向（竖屏）**尺寸，否则坐标会被缩放；
* 游戏用的横屏坐标换到 HID 坐标是 `(面板宽 − y, x)`。

## 三、音符来自谱面数据，不来自画面

画面只用在一个很粗的判断上：**现在是不是乐队确认页**（对 LIVE START 按钮做模板匹配，
顺便拿到了比写死坐标更可靠的按钮位置）。

其余——哪个音符、哪条轨、什么时刻、什么手势——全部来自谱面数据。相比从视频流里识别音符：

* 精确（没有识别误差）；
* 便宜（不用解码）；
* 稳定（不会漂）。

## 四、手势：长条会动，尾巴会甩

把 340 张谱面全部解析后是这样：

| 事实 | 数量 |
| --- | --- |
| 音符总数 | 95190 |
| 长条 | 23073 |
| 头尾位置不同的长条 | 11986 |
| 中途会移动的长条（含滑出去又滑回来的） | 15311 |
| **尾巴**是轻扫的长条 | 2512（上滑 1536 / 左滑 492 / 右滑 484） |
| **头部**是轻扫的长条 | 200 |
| 独立的轻扫音符 | 6698（只有上 / 左 / 右，没有下滑） |

长条的横移速度实测**中位 1258 px/s、90 分位 4346 px/s**。手指原地不动，或者每个谱面
节点（约 157ms）才动一次（单步 197px），都会让手指有相当一部分时间在条外——
表现出来就是"看起来随机"的间歇性 miss。改成沿轨迹**按位移重采样**（每走约 50px 发一次
划动、同一根手指最快 40Hz）后，单步中位降到 72px。

尾巴是轻扫的长条要按顺序做三件事：先**贴在条子尾巴的位置**、再**划出去**、最后**松手**。
漏任何一步都会掉。

## 五、试过但放弃的

写出来是为了让别人少走这几周：

* **画面闭环对时**（用屏幕上的音符反推偏移）：一次误检就把排程推偏 ±400ms。
  代码里还留着观测版，但默认关闭。
* **音频时钟**（读游戏自己的播放位置）：唯一能读到的计数器每 5 秒才更新一次，
  出现时第一个音符早就过去了；而且那条日志其实是主界面 BGM 的。
* **`sendevent` / `minitouch`**：这台机器上被拒或不可用。
* **用加载页猜前摇**：方差 9 秒，见上。

## 六、怎么验证

能离线验的都不上手机：

* **340 张谱面**全部跑一遍解析 + 排程回归（0 失败）；
* 检查排程里有没有"手指还没松开就被再次按下"（0 次）、同刻是否"先按后松"；
* 把手势形状打出来肉眼核对（尾巴右滑的长条会变成：贴位 → +60px → +120px → 松手）；
* 上机后日志会记下锚点、接管位置、手势构成、以及有没有动作迟到。
